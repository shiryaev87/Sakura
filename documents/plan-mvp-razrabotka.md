# План разработки MVP «Sakura» для пилотного застройщика

**Дата:** 27.09.2026
**Цель:** за 12 недель (6 спринтов по 2 недели) довести продукт до состояния, пригодного для платного пилота на одном реальном посёлке.
**Команда:** 1 разработчик (Go, junior→middle). Оценки даны в человеко-днях (ч/д) с запасом на неопытность.

---

## 1. Что такое MVP (и что им не является)

### 1.1. Гипотеза пилота
> Мелкий застройщик/владелец посёлка готов платить за сервис, который даёт покупателю забронировать участок онлайн с оплатой задатка — без звонка менеджеру — и автоматически освобождает бронь, если сделка не состоялась.

### 1.2. Критерии успеха пилота (фиксируем ЗАРАНЕЕ, до кода)
| Метрика | Порог продолжения |
|---|---|
| Доля броней через сайт (vs звонки/мессенджеры) | ≥ 30% всех броней за пилот |
| Конверсия посетитель → бронь | ≥ 3% от целевых визитов |
| Доля броней, доведённых до сделки | ≥ 40% |
| Доля автоистёкших броней | ≤ 35% (иначе правим сроки/задаток) |
| Готовность застройщика платить после пилота | ≥ 1 из 1 🙂 (и 2–3 рекомендации коллегам) |

Если после 6–8 недель пилота метрики ниже порогов — продукт не подтвердился, масштабирование не начинаем.

### 1.3. В MVP входит
1. Публичная страница посёлка: схема участков (SVG), статусы, цены, кнопка «Забронировать».
2. Регистрация покупателя: телефон + SMS-код (email — опционально).
3. Бронь с онлайн-оплатой задатка (ЮKassa / СБП).
4. Автоистечение брони по таймеру (дефолт 72 ч, настраивается продавцом).
5. Кабинет продавца: список броней, подтверждение, смена статусов, экспорт.
6. Уведомления: покупателю и продавцу (SMS/email) о брони, истечении, сделке.
7. Простая админка самообслуживания: продавец сам загружает схему и участки.

### 1.4. В MVP НЕ входит (осознанно)
- Мультилендинги, конструктор сайтов, блоги → это потом.
- CRM с воронками, задачами, звонками → интеграция с amoCRM через API, не дублируем.
- Регистрация сделок в Росреестре, генератор договоров → ручной этап, за пределами MVP.
- Кадастровый импорт из DXF/ЕГРН → в MVP загрузка SVG/DXF вручную, привязка к карте не нужна.
- Мобильное приложение → адаптивный веб достаточно.
- Маркетплейс «много посёлков у разных продавцов» → пилот на ОДНОМ посёлке, но модель данных — мульти-tenant сразу.

## 2. Решения по архитектуре (принять до Спринта 0)

| Вопрос | Решение | Почему |
|---|---|---|
| Мульти-tenant | Да, `seller_id` везде с первого коммита | Переделка потом = рефакторинг века |
| БД | PostgreSQL (есть), миграции golang-migrate | Уже выбрано, остаётся |
| Redis | Для таймеров брони + rate limiting + кэш сессий | В compose уже есть, наконец используем |
| Платежи | ЮKassa (СБП + карты). Задаток = платёж с холдом/возвратом | Самый быстрый онбординг юрлица в РФ |
| SMS | sms.ru или Twilio-alternative (сравнить цены) | Нужна верификация телефона покупателя |
| Фронт | Оставить htmx + шаблоны (не уходить в SPA) | Скорость разработки; SEO из коробки |
| Деплой | VPS (Timeweb/Selectel) + Docker + Caddy (HTTPS из коробки) | Дёшево, просто, сертификаты автоматом |
| Мониторинг | Uptime-kuma + логи в stdout + Grafana позже | Не усложняем |

**Техдолг, закрываемый в Спринте 0:** секреты в env, миграции, синхронизация схемы БД с кодом (`users`, `plots.reserved_by` отсутствуют в `create_tables.sql`), CI (lint + тесты на GitHub Actions / GitLab CI).

## 3. Спринт-план

### Спринт 0 — Фундамент (недели 1–2, ~8 ч/д)
- [ ] Конфигурация через переменные окружения (godotenv + env), убрать хардкод паролей и ключа сессии — 1 ч/д
- [ ] Пакетная структура проекта: `cmd/`, `internal/handlers`, `internal/store`, `internal/auth`, `migrations/` — 1 ч/д
- [ ] golang-migrate: актуальная схема БД (`sellers`, `villages`, `plots`, `users`, `bookings`, `payments`) — 2 ч/д
- [ ] GitHub Actions: golangci-lint + `go test` + `go build` на каждый push — 1 ч/д
- [ ] Базовые тесты на auth-хендлеры (регистрация/логин) — 2 ч/д
- [ ] Docker: Dockerfile для приложения, compose с app+postgres+redis — 1 ч/д

**Результат:** код деплоится на сервер одной командой, секретов в репозитории нет.

### Спринт 1 — Аутентификация и роли (недели 3–4, ~10 ч/д)
- [ ] Роли: `buyer`, `seller`, `admin` (поле в users + middleware) — 1 ч/д
- [ ] Регистрация покупателя: телефон + SMS-код, сессия после подтверждения — 3 ч/д
- [ ] Регистрация продавца: email + пароль, ручная активация админом (на пилоте — застройщик один) — 2 ч/д
- [ ] Восстановление доступа (код по SMS) — 1 ч/д
- [ ] Rate limiting на /login, /register, /verify (Redis, токен-бакет) — 1 ч/д
- [ ] Обновить все шаблоны под роли — 2 ч/д

**Результат:** два типа пользователей с разными сценариями.

### Спринт 2 — Кабинет продавца и загрузка посёлка (недели 5–6, ~12 ч/д)
- [ ] CRUD посёлка: название, описание, фото, адрес/координаты — 3 ч/д
- [ ] Управление участками: список, импорт из CSV (номер, площадь, цена), ручное редактирование — 3 ч/д
- [ ] Загрузка схемы: SVG-файл + привязка полигонов к участкам через простой редактор (click по полигону → выбор номера) — 4 ч/д ⚠️ *самая рискованная задача MVP, закладываем буфер*
- [ ] Смена статусов участка вручную: available / reserved / sold / hidden — 1 ч/д
- [ ] Дашборд продавца: счётчики (брони, сделки, сумма задатков) — 1 ч/д

**Результат:** продавец сам за день заводит свой посёлок без разработчика.

### Спринт 3 — Движок бронирования (недели 7–8, ~12 ч/д)
- [ ] Таблица `bookings`: участок, покупатель, сумма задатка, срок, статус — 1 ч/д
- [ ] Операция брони: транзакция БД (UPDATE … WHERE status='available'), защита от гонок — 2 ч/д
- [ ] Таймер автоистечения: воркер (горутина + Redis), освобождение участка, событие — 2 ч/д
- [ ] Лимиты: 1 активная бронь на покупателя, опционально — запрет повторной брони без менеджера — 1 ч/д
- [ ] Уведомления: шаблоны SMS/email на события (создана, истекает за 24 ч, истекла, подтверждена, сделка) — 3 ч/д
- [ ] Кабинет покупателя: мои брони, счёт-ссылка на оплату, статус — 2 ч/д
- [ ] Кабинет продавца: очередь броней, подтвердить / отменить с возвратом — 1 ч/д

**Результат:** полный цикл брони без денег (статус «ожидает оплаты» заглушкой).

### Спринт 4 — Платежи и задаток (недели 9–10, ~10 ч/д)
- [ ] Интеграция ЮKassa: создание платежа, webhook обработка — 4 ч/д ⚠️ *тестовый контур + согласование документов юрлица может занять дольше, начать оформление на Спринте 2*
- [ ] Логика задатка: оплата → бронь активна; истечение → авто-возврат; сделка → зачёт; отмена продавцом → возврат — 3 ч/д
- [ ] Юридические тексты: публичная оферта брони, согласие на обработку ПД — 2 ч/д *(привлечь юриста, 1 консультация)*
- [ ] Экран оплаты и экраны результатов — 1 ч/д

**Результат:** деньги ходят, бронь имеет юридический вес.

### Спринт 5 — Публичная витрина и SEO (недели 11–12, ~10 ч/д)
- [ ] Публичная страница посёлка: красивый лендинг + схема + FAQ + контакты продавца — 3 ч/д
- [ ] SEO: мета-теги, OpenGraph, sitemap.xml, микроразметка Product/Offer, ЧПУ /poselok/{slug} — 2 ч/д
- [ ] Страница отдельного участка: /poselok/{slug}/uchastok/{number} с фото и описанием — 2 ч/д
- [ ] Аналитика: Яндекс.Метрика + цели (клик «Забронировать», оплата) — 1 ч/д
- [ ] Адаптивность под мобильные (таблицы/схема) — 2 ч/д

**Результат:** продавец получает не «личный кабинет», а канал лидов — аргумент для подписки.

## 4. Бюджет и риски

### Трудозатраты
| Спринт | ч/д |
|---|---|
| 0 | 8 |
| 1 | 10 |
| 2 | 12 |
| 3 | 12 |
| 4 | 10 |
| 5 | 10 |
| **Итого** | **~62 ч/д (~3 календарных месяца на 1 разработчика)** |

Дополнительно (вне разработки):
- Консультация юриста по задатку и ПД — 1 встреча, до Спринта 4.
- Подключение ЮKassa — заявка и документы подать на Спринте 2, сроки рассмотрения не наши.
- SMS-шлюз: сравнить тарифы sms.ru / smsaero / twilio, выбрать на Спринте 1.

### Топ-5 рисков
1. **Редактор привязки полигонов** раздуется → фолбэк: разработчик готовит SVG за 2 ч вручную для пилота, редактор откладывается.
2. **ЮKassa отклонит заявку** застройщика → фолбэк: СБП через другой банк-партнёр; в крайнем случае бронь с ручным подтверждением оплаты (удерживаем пилот, теряем метрику).
3. **Рассинхрон вебхуков платежей** → идемпотентность по `payment_id`, сверка по расписанию (джоба раз в час).
4. **Покупатели не доверяют онлайн-оплате** → задаток минимальный (5–10 тыс. ₽), чёткая оферта, телефон продавца на видном месте.
5. **Один разработчик заболел/сгорел** → каждый спринт должен заканчиваться работающим деплоем; никаких «фич в разработке» длиннее спринта.

## 5. Что делать параллельно с разработкой (нельзя откладывать)

1. **Неделя 1–2:** найти пилотного застройщика. Критерии: посёлок 30–150 участков, есть менеджер продаж, участки продаются дольше 6 месяцев. Договориться: бесплатный пилот 8 недель в обмен на метрики и отзыв.
2. **Неделя 3–4:** интервью ещё 5–7 застройщиков (даже без намерения пилотировать) — проверить, что проблема формулируется ими так же, как нами.
3. **Неделя 8–10:** подготовить тарифы и договор на подписку (пилотный и платный), чтобы после пилота не терять месяц на бумажки.
4. **Непрерывно:** после каждого спринта показывать живой прогресс застройщику — это и продажи, и ранний фидбек.

---

## 6. Определение «дальше» (после пилота)

- Метрики выше порогов → платная подписка с пилотника, 2–3 новых застройщика по рекомендации, Спринты 6+: онлайн-задаток-в-сделку, amoCRM-интеграция, кадастровый импорт, самооплата подписки внутри сервиса.
- Метрики ниже порогов → разбор: проблема в трафике (фиксим SEO/маркетинг), в конверсии схемы (фиксим витрину) или в самой гипотезе (боль не та / не такая). Решение о пивоте или закрытии — по данным, не по интуиции.
