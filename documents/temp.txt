4. Интерактивная схема участков — как реализовать

Два основных подхода:

A) SVG-карта с полигонами
Каждый участок — это <polygon> или <path> с id, привязанным к записи в БД. Цвет заливки меняется по статусу (зелёный/жёлтый/красный). Клик по полигону открывает карточку участка. Хорошо подходит, если у вас уже есть генплан в векторе (из AutoCAD/QGIS можно экспортировать в SVG).

B) Геокарта (Leaflet/Mapbox) + GeoJSON
Если нужна привязка к реальной местности (спутник, кадастровая карта) — участки как GeoJSON-полигоны поверх карты. Плюс: реальная гео-точность. Минус: чуть сложнее в разработке.

Для агентства недвижимости часто комбинируют: схематичный генплан (SVG) для удобства визуального выбора + отдельная кадастровая карта для точности.

5. Логика бронирования (важный момент)

Чтобы избежать конфликтов (два клиента жмут "забронировать" одновременно):

При клике "забронировать" — участок временно блокируется в Redis (TTL 15-30 минут)
Клиент вводит данные / вносит предоплату
После подтверждения — статус меняется в PostgreSQL, блокировка снимается
Если TTL истёк без оплаты — участок снова свободен

4. Ключевая механика: бронирование без гонок

Самое важное место, где Go реально показывает себя хорошо — конкурентный доступ к участку.

Вариант с Redis (рекомендую для старта):

go
func (s *BookingService) LockPlot(ctx context.Context, plotID string, userID string) error {
    key := fmt.Sprintf("plot_lock:%s", plotID)
    ok, err := s.redis.SetNX(ctx, key, userID, 15*time.Minute).Result()
    if err != nil {
        return err
    }
    if !ok {
        return ErrPlotAlreadyLocked
    }
    return nil
}

Плюс фоновый воркер (goroutine + time.Ticker или отдельный сервис) снимает бронь в БД, если оплата не пришла в течение TTL.

Вариант с PostgreSQL (для критичных операций, где важна консистентность):

sql
UPDATE plots 
SET status = 'reserved', reserved_by = $1, reserved_until = NOW() + INTERVAL '15 minutes'
WHERE id = $2 AND status = 'available';

Используем SELECT ... FOR UPDATE или атомарный UPDATE ... WHERE status = 'available' — если 0 строк обновлено, значит участок уже занят. Это надёжнее, чем полагаться только на Redis.

Лучшая практика — комбинировать: Redis для быстрой UX-блокировки (чтобы фронт сразу показал "занято"), PostgreSQL как источник истины с атомарными апдейтами.

Хороший вопрос — и да, это известная особенность SVG в браузерах, а не баг в вашем коде. Разберём, почему так происходит, и сразу исправим.

Почему участок пропадает

Когда htmx подменяет <g>...</g> внутри <svg> через outerHTML, браузер не всегда правильно понимает, что вставляемый кусок HTML должен обрабатываться как SVG-элементы (<polygon>, <g>), а не как обычный HTML. Это давний технический нюанс браузеров: SVG живёт в отдельном "пространстве имён", и частичная замена кусочка внутри него через стандартные механизмы иногда "теряет" эту привязку — элемент технически вставляется, но не отображается.

Решение — обновлять всю схему целиком, а не один участок

Вместо замены одного <g> будем перерисовывать всю <svg> целиком при каждом бронировании. Для 5-20 участков это абсолютно незаметно по скорости, а проблема с namespace исчезает полностью, потому что весь <svg> пересоздаётся браузером заново правильно.

Что изменилось:

У <svg> появился id="scheme"
hx-target="#scheme" теперь указывает на весь SVG-контейнер, а не на конкретный <g>
hx-swap="innerHTML" — заменяем содержимое внутри <svg>, сам тег <svg> остаётся на месте (это важно, иначе снова возникнет проблема с namespace)
Появился новый блок {{define "plots-svg"}} — общий кусок, который рисует все участки разом; используется и при первой загрузке страницы, и при бронировании

go
func reserveHandler(w http.ResponseWriter, r *http.Request) {
	id := r.PathValue("id")
	ctx := context.Background()

	_, err := db.Exec(ctx,
		"UPDATE plots SET status = 'reserved' WHERE id = $1 and status = 'available'", id)
	if err != nil {
		http.Error(w, err.Error(), 500)
		return
	}

	rows, err := db.Query(ctx,
		"Select id, number, area_sotka, price, status, svg_points From plots ORDER by id")
	if err != nil {
		http.Error(w, err.Error(), 500)
		return
	}
	defer rows.Close()

	var plots []Plot
	for rows.Next() {
		var p Plot
		err := rows.Scan(&p.ID, &p.Number, &p.Area, &p.Price, &p.Status, &p.SvgPoints)
		if err != nil {
			http.Error(w, err.Error(), 500)
			return
		}
		plots = append(plots, p)
	}

	tmpl := template.Must(template.ParseFiles("templates/index.html"))
	err = tmpl.ExecuteTemplate(w, "plots-svg", map[string]interface{}{"Plots": plots})
	if err != nil {
		log.Println("Ошибка рендеринга шаблона:", err)
	}
}

Что изменилось: убрали Redis-блокировку (если уже добавляли на прошлом шаге — верните её обратно, я убрал только для ясности примера, допишите SetNX/defer rdb.Del как раньше, если уже внедряли). Главное изменение — вместо чтения одного участка теперь читаем весь список и рендерим блок "plots-svg", а не "plot-card".
